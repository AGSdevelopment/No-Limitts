# RCA — staffhub-236 "staff can't sign in" (run 87a8ce13, deployed 2026-11-10 03:46:49Z / ~11:46am)

## Summary
Backend is healthy and the email/password route works. The real failure is **Microsoft/Entra sign-in**: every `GET /api/auth/microsoft/start` returns **HTTP 400 `{"detail":"Invalid return address"}`**, so the OAuth flow never even redirects to Microsoft. Because **all 40 staff accounts are Microsoft SSO (0 have a local password)**, this blocks effectively everyone. Today's deploy did NOT change auth code; the cause is a host mismatch in the backend's return-address allowlist vs. the web origin staff actually use.

## Evidence
- **Backend started cleanly:** `Uvicorn running on http://0.0.0.0:8001` immediately after promote (~03:47Z); `/health` returns 200 steadily. One transient `nginx upstream timed out` on `/health` at 08:07Z (single tier_0 replica blip), self-recovered.
- **No 5xx / no Python tracebacks on auth routes.** Status mix on auth routes over the last ~24h: `401` (wrong/no creds), `422` (malformed body), a few `429` (login rate-limit). The only "error"-level log line was the one nginx health timeout.
- **Microsoft route failing:** repeated `GET /api/auth/microsoft/start?redirect=https://staffhub-live.emergent.host/...` → `400`. Live probe confirmed body = `{"detail":"Invalid return address"}`.
- **Zero OAuth callbacks** (`/api/auth/microsoft/callback`) and **zero successful logins** (no `200` on `POST /api/auth/login` or `GET /api/auth/me`) observed in the window (logs capped/sampled, but the complete absence alongside ~97 401s is strong).
- **OAuth env present & non-empty:** `MS_CLIENT_ID`, `MS_CLIENT_SECRET`, `MS_TENANT_ID` all set. So this is NOT a missing-secret problem.
- **Users:** `users` count = 40; `password_hash`/`password`/`hashed_password`/`passwordHash` exist on **0** of them → all staff rely on Microsoft SSO.

## Root cause (code)
`backend/routes/auth.py`:
```
APP_SCHEMES = {"staffhub", "exp", "exps"}            # line 22
def safe_return(url: str) -> bool:                   # line 62
    p = urlparse(url or "")
    if p.scheme in APP_SCHEMES:
        return True
    own = urlparse(os.environ.get("PUBLIC_BACKEND_URL") or "").hostname
    return p.scheme in ("http","https") and (p.hostname == own or p.hostname == "localhost")

@router.get("/auth/microsoft/start")
async def ms_start(redirect: str):
    if not safe_return(redirect):
        raise HTTPException(400, "Invalid return address")   # line 84
```
`safe_return` accepts an http(s) return URL **only if its hostname equals `PUBLIC_BACKEND_URL`'s hostname** (or localhost, or a `staffhub://`/`exp://` deep link).

- Confirmed secret values (via matches_expected, values never revealed): `PUBLIC_BACKEND_URL` = `https://staffhub-236.emergent.host`, `REACT_APP_BACKEND_URL` = `https://staffhub-236.emergent.host`.
- Staff web app sends `redirect=https://staffhub-live.emergent.host/...` — a **different host** → `safe_return` returns False → 400.

### Reproduced (eph sandbox, pure logic, no secrets needed)
With `PUBLIC_BACKEND_URL=https://staffhub-236.emergent.host`:
```
False  https://staffhub-live.emergent.host/auth/callback
False  https://staffhub-live.emergent.host/
True   https://staffhub-236.emergent.host/auth/callback
True   http://localhost/auth/callback
```

## Why it is not today's code changes
Today's diff touched only web CSS / app.json web metadata / a label / clock-location fallback text — not auth. `PUBLIC_BACKEND_URL` is set on first deploy and is NOT overwritten on redeploy. So this is a pre-existing structural mismatch between the backend's allowlist and the web origin staff use (`staffhub-live.emergent.host`), surfaced/reported now — not introduced by the 11:46 redeploy.

## Suggested fix (pick one)
**Preferred — source (backend):** broaden `safe_return` to also accept the real production web origin(s). E.g. read an env allowlist `ALLOWED_RETURN_HOSTS` (comma-separated) and accept `p.hostname in allowed`, and/or allow the `*.emergent.host` suffix. Then add `staffhub-live.emergent.host` to that allowlist. This is the robust fix and keeps the Microsoft `redirect_uri` (= `PUBLIC_BACKEND_URL` + `/api/auth/microsoft/callback`, registered in Azure) unchanged.

**Alternative — no code change:** have staff use `https://staffhub-236.emergent.host` (the host that already matches) instead of `staffhub-live.emergent.host`. NOTE: do NOT simply repoint `PUBLIC_BACKEND_URL` to `staffhub-live` — that also changes the Microsoft `redirect_uri`, which must then be re-registered in the Azure app registration, or the callback will fail.

## Handoff
Backend source fix in `backend/routes/auth.py` (`safe_return` / return-address allowlist). After applying, redeploy and confirm `GET /api/auth/microsoft/start?redirect=<prod-web-origin>` returns a 302 to `login.microsoftonline.com` instead of 400.
